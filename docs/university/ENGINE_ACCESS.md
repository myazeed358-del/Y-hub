# University phase 1 — exceptional engine permissions

Base main is 8a5dde1b20f26161e7e26b8b0bf71ecd1097f136, freshly fetched and remotely checked. Phase 3 remains on separate branches; no completed functionality was rewritten. Migration numbers 0029–0032 are reserved by Phase 3. This independent branch starts new work at **0033_exceptional_engine_access.sql**. No production writes or migration application.

Instructors delegate only engine-kind modules whose teaching major matches their current profile (or a subject-unrestricted engine), whose roles allow both student and instructor, and which have no additional resource permission requirements. Legacy ability to browse other engines is not authority to delegate them. Admin/Owner can review and revoke; they cannot impersonate instructor grants. Each grant references an actual section, enrolled student, current instructor and server-bounded expiry (at most 366 days). Duplicate active requests return the existing grant; extending a grant requires revoking and issuing a new grant.

Locks serialize actor/recipient roles, policy, section assignment and enrollment with creation. Current database predicates recheck all conditions on every permission/compute request, with no trusted browser actor/role payload. Expiry requires no scheduler. Withdrawal/deletion, instructor reassignment or actor/recipient role/major changes permanently revoke old grants, so re-enrollment/re-promotion cannot resurrect them. All grant mutations are audited atomically; forced audit failure rolls back the grant. Grants and policy tables have RLS and no client mutation privileges. Read scope: student own rows, current instructor own sections, Admin/Owner review all. Backend private functions/tables are inaccessible to browser roles.

The `/engine-access` API-v2 application uses existing section tables and the existing active-roster RPC. It supports section/student/eligible-engine/expiry selection, history, confirmation and revocation, bilingual labels, existing design tokens and responsive layout. No central route/engine list registration. New navigation inventory assertions include only the intended staff route.

`tools/export_module_policy.mjs` derives deployment SQL from trusted enabled manifests. Adding a compliant module requires no central list edit; generate/review policy SQL as part of that module's deployment. Browser clients cannot register policies. Compute protocol bindings are separately reviewed backend-operation authorization policies, not a UI catalog. Future protected operations need explicit backend bindings. Resource-permission modules fail closed in generic eligibility.

AuthContext resolves server permissions and refreshes every 30 seconds/on focus, removing failed/stale-account responses. Grants relax only engine major restrictions, never roles/resource permissions. Navigation/layout/route checks reuse the existing module selectors. This UI cache is not an authorization boundary: Python HTTP requests independently verify the actual JWT through Supabase and current database permission on every call, fail closed on configuration/network errors, and do not cache positive authorization. Both phase and optional AST endpoints use the shared authorization boundary. Local mathematical algorithms, already delivered as JavaScript, are not DRM-protected against copying; no absolute claim of preventing offline reuse is made.
